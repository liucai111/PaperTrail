# PaperTrail｜五分钟项目演示与答辩脚本

> **定位**：适用于实习面试、课程展示和 GitHub 项目讲解。建议用 **`D:\PaperTrail` 完整的本地私有环境**演示既有论文、问答、笔记和实验结果；公开仓库不含 PDF/Gold/原始 QA，不要把公开版当成已带数据的现场演示环境。
>
> **演示原则**：优先展示保存的真实结果，不在五分钟内等待新一轮模型调用；不把 LLM Judge 评分描述为人工核验；不把引用字符串匹配当成事实支持。

## 一、五分钟时间安排

| 时间段 | 画面 / 操作 | 必须讲清楚的内容 |
|---|---|---|
| 00:00–00:30 | PaperTrail 首页 / PDF 阅读工作台 | 项目要解决什么痛点、定位是什么 |
| 00:30–01:10 | 选择 LightRAG 或已 ready 的论文，展示 PDF | 论文原文与问答在同一屏；版本、页码与阅读状态 |
| 01:10–02:15 | 打开一条已保存的完整问答，展示初始答案、Claim、Evidence，点击来源跳转 | BM25 + Dense + RRF；证据可定位但不等于自动证明支持 |
| 02:15–02:55 | 保存/查看一条已有证据笔记，再切到历史问答 | 笔记、历史与来源版本绑定；刷新恢复 |
| 02:55–03:45 | 打开跨论文方法比较报告 | 同题比较多篇论文，并保留各条结论的来源与限制 |
| 03:45–04:35 | 真实 RAG 实验结果页面 | 开发集/独立测试分开展示，解释 Hybrid 对比结果和不足 |
| 04:35–05:00 | 总结技术亮点与边界 | 混合检索、证据核验、任务恢复、真实评测，不夸大 Repair |

## 二、可以直接照读的讲解词

**00:00–00:30｜开场**

“PaperTrail 是我做的论文原文阅读与证据驱动 RAG 问答工作台。阅读论文时，传统聊天工具经常只给出一个看似合理的结论，但不容易核对原文，也不方便长期积累笔记。所以我把 PDF 阅读、检索、答案核验、原文引用和研究记录放到了同一个工作流里。”

**00:30–01:10｜PDF 阅读**

“左侧是论文库，中间是 PDF.js 阅读器，右侧是答案工作区。这里保存论文的版本与页码信息，阅读区可以调整比例，切换历史问答还能恢复对应页码。PDF 解析采用 PyMuPDF；遇到部分无法直接提取的内容，可以走可选 OCR，但复杂图表不保证完全准确。”

操作：打开一篇已经显示 **ready** 的论文，确认第一页不空白、适合宽度；快速关闭和打开左侧论文库，再返回原布局。不要现场重新解析 PDF。

**01:10–02:15｜问答与原文证据**

“当我针对当前论文提问时，系统先使用 BM25 做词面召回，再通过 Dense Embedding 得到语义候选，最后使用 RRF 融合排序。模型依据检索证据回答，再把答案拆成 Claim，对照引文给出模型辅助的支持状态。这里可以点击详细证据跳到 PDF 对应页并查看高亮。”

“我特意把来源定位和语义支持分开：即使在 PDF 中找到相同的文字，也不能仅凭字符串匹配就认为结论已经成立；未核实和证据不足会被如实保留。”

操作：打开事先准备的历史成功问答。展示简洁答案，滑到 Claim/Evidence 详情；点击一条可用的“查看原文”，确认 PDF 跳页和高亮。不要选无法复现的引用跳转作为现场演示样本。

**02:15–02:55｜笔记与历史**

“用户不仅能提问，还可以为答案和引用做证据笔记，并从历史记录回到对应论文和页码。这部分持久化在本地 SQLite 中，避免一次对话结束后丢失研究上下文。”

操作：展示一条已保存的笔记；打开历史问答并切回刚才的文章。若时间紧张，优先展示已保存状态，不必再新增记录。

**02:55–03:45｜多论文方法对比**

“对研究型任务，仅看一篇论文不够。因此系统提供跨论文方法比较：限定选择的论文版本，从不同文献中整理方法、差异和引用；报告可以保存、导出，人工修订也会生成独立版本，不会覆盖之前的历史。”

操作：直接打开一份已保存的方法比较报告，选两行分别来自不同论文的证据；强调“来源约束 + 版本可追溯”。

**03:45–04:35｜真实实验与客观边界**

“我还做了真实的离线实验，不只展示界面。Stage 16A5 的冻结开发集共有 72 题，66 题完成 Basic/Hybrid 配对。其中新增 48 题有 45 组有效 LLM Judge 配对：Accuracy 的 0–4 分平均分从 3.422 提高到 3.867，Faithfulness 从 3.756 到 3.933。换算成满分归一化得分是 85.6% 到 96.7%、93.9% 到 98.3%，**这里的百分比不是实际答题正确率**。”

“Stage 16A6 是论文级隔离的独立文本测试，30 题、60 条实验条件，成功 QA 48 条，只有 17 组有效配对评分。因为 Judge 协议不同，不能直接和开发集合并。正式 qrels 覆盖不足，所以我们没有伪造 Precision、Recall 或 MRR；Repair 的独立质量收益也还没有得到证实。”

操作：展示两栏卡片、两阶段不同协议/样本量和底部限制说明。不要展开所有技术日志，也不需要在现场重新运行 Judge。

**04:35–05:00｜结语**

“PaperTrail 的核心工作不只是接一个大模型 API，而是围绕真实 PDF 做可定位证据的数据链路，设计混合检索与 Claim 核验，并处理外部 Embedding 超时、重复请求、断点索引和持久化任务等工程可靠性问题。最终交付包括可运行的前后端、只读实验结果、自动化测试、架构说明，以及和私有实验数据隔离的公开 GitHub 版本。”

## 三、演示前准备（建议 10 分钟）

- [ ] 用 `scripts\papertrail.cmd doctor`、`start`、`status` 确认本地 API 8011 和 Web 5181 正常；不要同时启动两套冲突进程。
- [ ] 准备 **1 篇已 ready 的论文**、**1 条引用能够正常跳转的问答**、**1 条笔记**、**1 份跨论文比较报告**。
- [ ] 确认 PDF 第一页显示、侧栏收放、证据跳转与历史恢复均正常。
- [ ] 打开实验结果页，先记住两组有效配对的样本量 n=45 / n=17，不混用协议。
- [ ] 关掉 API Key / `.env` / SQLite 管理工具以及含私人数据的终端窗口。
- [ ] 演示尽量复用已持久化记录；不要当场上传新论文或开始整批向量化。
- [ ] 准备 README 中的截图作为 **断网或浏览器故障兜底**，并明确说明这是此前实际运行截图。

## 四、常见现场故障及替代演示

| 问题 | 现场处理 |
|---|---|
| Embedding 网络超时或 `outcome_unknown` | 不继续未知请求重发；切到已有 ready 论文与历史问答 |
| API 模型调用响应慢 | 展示已保存生成结果、核验详情与原文定位；说明为真实运行记录 |
| PDF 首屏偶发空白 | 先使用已有成功截图，再确认正确论文/页码；不要反复强制刷新耗费时间 |
| 独立测试指标被问到显著性 | 回答“目前为有限样本 LLM Judge 描述性结果，尚不能做普遍提升结论” |
| 被问到 Repair 是否显著改善 | 回答“开发集仅 2 次真实触发，评分 4→4，未观察到已验证的收益” |
| 公开仓库没有论文样例 | 回答“出于版权、数据隔离和评测安全，公开版仅含代码及脱敏汇总” |
