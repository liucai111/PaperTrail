# PaperTrail｜简历项目描述、项目亮点与面试问答

## 一、简历精简版（适合 1 页简历）

**PaperTrail — 论文原文阅读与证据驱动 RAG 问答平台**  
**技术栈**：Python、FastAPI、Vue 3、TypeScript、SQLite、PyMuPDF、PDF.js、BM25、Dense Embedding、RRF、DeepSeek

- 设计并实现一体化论文阅读与证据问答工作台，构建 **PDF 解析/分块 → BM25 + Dense + RRF 检索 → LLM 生成 → Claim 级核验 → PDF 引用定位** 的可追溯流程，支持历史问答、证据笔记及跨论文对比。
- 实现 **SHA-256 文档去重、SQLite 持久任务、Embedding 缓存与断点索引**，区分已成功、明确失败及 `outcome_unknown` 请求，减少网络中断后的重复处理和潜在重复费用。
- 组织冻结开发集与独立测试的真实对照实验：新增开发题 **45 组有效 LLM Judge 配对**中，Hybrid 相对 Basic 的 Accuracy 均分 **3.422→3.867/4**、Faithfulness **3.756→3.933/4**；分层报告成功率、失败样本与检索标注限制。

> 上述表述只描述可观察事实和个人参与的工程工作。如为多人协作开发，应将“设计并实现”调整为实际负责模块，不写成不存在的独立贡献。

## 二、技术细节加强版（投递 AI 应用 / 大模型工程 / 软件工程实习）

**项目背景**：将学术 PDF、可定位原文和 LLM 问答放在一个本地优先的研究工作台中，解决普通对话式阅读的引用不可追溯、答案支持性不明和研究记录易丢失问题。

**职责与实现（根据实际贡献选择）**

1. **混合检索与证据链路**：基于 PyMuPDF 构建页码、来源块和 chunk 对应关系，联合 BM25 与 `text-embedding-v4` Dense 召回，通过 RRF 融合 Top-k；在答案详情中保留证据、版本与 PDF 原文跳转。
2. **核验和受限修订**：将回答拆分为 Claim，分别记录引文原文、支持状态与缺失证据；只在规则触发时执行有界补检索与最多一次 Repair，保存修订前后的完整追踪记录，不将字符串命中误写为事实正确。
3. **可靠任务与全链路持久化**：采用 SHA-256 去重、SQLite 状态机与逐批原子向量落盘，支持上传任务和历史问答恢复；外部 Embedding 超时的未知结果不自动重发，以保留审计和费用边界。
4. **真实实验与工程交付**：冻结 72 题开发集和 30 题论文级隔离的独立文本测试；开发新增 48 题中 47 题完成 QA 配对、45 组有效 Judge，Hybrid 对 Basic 在这部分样本的 0–4 分量表上有正向差异；保留评分协议、失败率、Repair 触发与 qrels 覆盖不足的限制。完成可运行前后端、Mock 测试、README/部署文档和脱敏公开仓库。

## 四、面试 30 秒介绍

“PaperTrail 是一个证据驱动的论文 RAG 平台。我把 PDF 阅读器与问答整合起来，使用 BM25、向量检索和 RRF 融合生成检索候选；模型回答后会进行 Claim 级证据核验，详细引用可以直接定位到原文。工程上重点解决了上传文档时 Embedding 超时、断点恢复和结果未知不能安全重发的问题。项目还做了开发集和独立测试的真实对照实验，并把样本量、失败和评测局限完整记录下来。”

## 五、面试一分半讲解（项目难点）

“核心难点有三类。第一是检索与定位一致性：PDF 解析成 source block 后再分 chunk，如果回答引用只保留纯文本而丢失页码/版本，就不能可靠回到原文，因此要在索引与 Evidence 中保存来源关系。第二是答案支持性：引用字符串匹配并不等于事实成立，我把初始答案、Claim、证据支持状态和 Repair 分开保存，并限制自动修订次数。第三是外部 API 可靠性：向量接口有时超时，但客户端不知道服务端是否处理成功。我通过按模型/文本哈希缓存、逐批落盘、SQLite 任务状态以及 `outcome_unknown` 的显式确认处理来降低重复请求风险。最终实验显示在新增开发题的 45 个有效配对上，Hybrid 的 LLM Judge 均分高于 Basic，但我没有把它描述成普遍正确率或独立 Repair 收益。”

## 六、建议准备的面试追问

**Q1：为什么同时用 BM25、Dense 和 RRF？**  
A：BM25 对精确术语、论文缩写和实体匹配有效，Dense 对语义变体更有帮助。RRF 能在不直接比较不同检索分数标度的情况下融合排序。是否真正改善，应以相同题目、相同生成协议的真实配对结果验证。

**Q2：如何保证引用真的支持答案？**  
A：无法仅靠引文命中保证，所以分别记录原文字符串匹配、PDF 来源定位和模型辅助支持判断。对缺失证据的 Claim 保留未核实状态；核验模型本身同样可能出错，因此不能把 `supported` 当成人工真值。

**Q3：Embedding 超时为什么不能立刻重试？**  
A：客户端发生读取超时不意味着请求未被远端处理。若结果未知而重发，可能重复处理和计费。故把“确定未发送 / 已成功落盘 / 结果未知”作为不同状态，只自动继续明确未发送的部分，未知批次须显式授权。

**Q4：为什么开发集分数与独立测试不能直接合并？**  
A：两组使用不同 Judge 协议、流程组合和有效评分样本，且独立测试的样本较少。可以分层展示，而不能混合成一个看似精确的平均分或显著改善结论。

**Q5：Verifier 和 Repair 有哪些已验证收益？**  
A：已得到 Claim 状态分布和可追溯的核验过程；开发集两次 Repair 触发的前后评分都是 4→4，不能声称修复显著提升质量。后续需要独立 Claim 真值、更多实际触发以及拆分模块的消融实验。

**Q6：怎么防止运行时读到 Gold？**  
A：把生成/检索阶段的输入与离线评分阶段隔离，运行时只可得到 Question/论文版本与检索内容；Gold 和 Rubric 只在评分器读入，并检查运行记录与冻结哈希。
